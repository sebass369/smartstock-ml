# Phase 7B — Simple Machine Learning Model

## Purpose

Phase 7B adds the project's first trained machine-learning model. It fits one
global linear regression on daily synthetic demand, predicts the next complete
14-day delivery cycle, and compares the result against both Phase 7A methods.

Phase 7B forecasts demand only. It does not change the Phase 7A contract, the
Phase 4B ordering policy, inventory simulation, or any generated byte contract.
It adds no CLI, no YAML configuration, no serialized model, and no prediction
CSV.

All records and results are synthetic. They do not establish real-world
accuracy, operational benefit, or ordering performance.

## Problem formulation

The model is trained on **daily** product-level demand and its 14 daily
predictions are summed into one cycle total:

```text
training rows at origin O = every (date, product) record with date < O
daily prediction          = model(product_id, weekday)
cycle prediction          = sum of the 14 clipped daily predictions
```

Daily prediction on 14-day cycle totals was chosen over three alternatives:

- **Training directly on cycle totals** is degenerate. At the first origin only
  one completed cycle exists, giving 9 rows for 9 product levels and zero
  residual degrees of freedom. Every 14-day window is also weekday-balanced, so
  cycle totals contain no weekday variation at all.
- **One model per product** produces 27 separate fits and higher variance while
  yielding the same cycle totals as the global model.
- **A global model** pools 126 to 378 rows for the six shared weekday
  coefficients, keeps all nine products in a single fitted object, and stays
  non-degenerate at every origin.

Daily predictions are an internal implementation detail. Phase 7B defines no
daily record contract and reports no daily error metric. The official
evaluation is the 14-day cycle-total comparison.

## Target and prediction timing

Phase 7B reuses the three approved Phase 7A forecast origins without change.
The shared origin list comes from `list_complete_forecast_origins`, so Phase 7A
and Phase 7B can never disagree about which cycles are eligible.

| Forecast origin | Training dates (`date < O`) | Training rows | Target period |
| --- | --- | ---: | --- |
| 2025-01-21 | 2025-01-07 through 2025-01-20 | 126 | 2025-01-21 through 2025-02-03 |
| 2025-02-04 | 2025-01-07 through 2025-02-03 | 252 | 2025-02-04 through 2025-02-17 |
| 2025-02-18 | 2025-01-07 through 2025-02-17 | 378 | 2025-02-18 through 2025-03-03 |

There are 27 default records: three origins multiplied by nine products, in
stable forecast-origin order and `products.yaml` product order. An incomplete
future cycle is skipped rather than partially scored.

The model is **refitted independently at each origin**. This is required by the
expanding-window design: at each origin the model may use everything before it
and nothing on or after it. Fitting once on the full dataset would leak later
demand into earlier origins, and fitting once on the first window would discard
the expanding history the Phase 7A candidate is allowed to use.

`build_training_rows` accepts the **complete** demand dataset and filters it
with `record_date < forecast_origin_date`. The presence of later records is
expected and is never a reason to reject the dataset. Every returned training
row is then validated as strictly pre-origin.

## Feature contract

The model uses exactly two inputs, both known on the forecast origin date:

| Feature | Type | Encoding | Calculation | Availability |
| --- | --- | --- | --- | --- |
| `product_id` | string | one-hot, categories from the approved alias list, first level dropped | copied from the record | always, from configuration |
| `weekday` | string | one-hot, categories from `ENGLISH_WEEKDAYS`, first level dropped | `get_english_weekday(target_date)` | always, from the calendar |

Both category lists are fixed in code rather than inferred from the training
slice, so the encoded column order is identical at every origin.

### Excluded because they carry no information beyond the product alias

`pack_size_units`, `open_shelf_life_days`, `unopened_shelf_life_days`,
`primary_risk`, and `demand_level` are constant per product and therefore
perfectly collinear with the product one-hot columns. `month` is excluded
because the dataset spans January through March only, and the first origin's
training window contains January alone.

### Excluded because of leakage

Same-day and future `demand_units`; any lagged demand or rolling statistic that
reads a date on or after the origin; `fulfilled_demand_units`, `units_used`, and
`unmet_demand_units`; every Phase 4A inventory, expiration, waste, and stockout
outcome; and Phase 4B ordering recommendations.

The governing rule for any lag feature is that a lag of `k` days is admissible
for the whole target window only when `t - k <= O - 1` holds for the last target
date `t = O + 13`, which requires `k >= 14`. Phase 7B uses no lag or rolling
features. Recursive multi-step forecasting, where a prediction becomes the next
step's input, is rejected because it compounds error over 14 steps and cannot be
validated honestly on three origins.

### `is_high_demand_day` is excluded

`is_high_demand_day` is known in advance from configuration, so excluding it is
not a leakage decision. It is excluded for three other reasons:

1. It exposes a synthetic generator rule. The generator computes
   `demand_units = randint(range) + 1` exactly when this flag is true, so a
   model given the flag is copying a project-authored rule rather than learning
   a pattern.
2. It depends partly on provisional configuration. `high_demand_days` appears in
   `provisional_fields` for `Whole_Milk`, `Cold_Foam_A`, `Whipped_Topping`,
   `Skim_Milk`, and `Oat_Beverage`.
3. It would make the demonstration artificially favorable.

The flag is **not** redundant with the additive `product_id + weekday` feature
space. It equals `weekday in product.high_demand_days`, which is a function of
the product and weekday *interaction*, so an additive model cannot reproduce it
and adding it would change the fitted daily values. It is redundant only against
a fully saturated product-by-weekday model.

## Model and fixed parameters

Phase 7B uses ordinary least squares, `LinearRegression(fit_intercept=True)`,
and not Ridge regression.

- **No hyperparameter.** With only three evaluation origins there is no
  leakage-safe way to select a regularization strength. Holding out an origin
  for inner validation would reduce the evaluation to two origins and break the
  shared 27-record comparison.
- **The design is already well conditioned.** Every product appears on every
  date, so the training design is a balanced complete layout. After dropping one
  level per category the matrix is full rank with 15 parameters against 126 to
  378 rows. Ridge's stabilization rationale does not apply.
- **Ridge shrinkage here would be encoding-dependent and substantively wrong.**
  With the first level dropped, Ridge shrinks product coefficients toward an
  arbitrary reference product rather than toward the overall mean, so the result
  changes if a different level is dropped. The between-product spread runs from
  roughly 14 to 69 units per cycle, and that spread is the signal the model is
  supposed to capture.
- **Coefficients stay readable.** Each one is an adjustment in demand units per
  day, which is the clearest possible explanation of a fitted model.

The pipeline has two steps and no scaling step. All features are zero-or-one
indicator columns on a single scale, so scaling would add a moving part without
any benefit.

```text
step 1  ColumnTransformer -> OneHotEncoder(product_id, weekday)
        fixed categories, first level dropped, unknown category raises an error
step 2  LinearRegression(fit_intercept=True)
```

In plain English: step one turns the product name and the weekday into indicator
columns, using category lists taken from project configuration so the columns
are always in the same order. Step two adds a baseline number, a per-product
adjustment, and a per-weekday adjustment to estimate one day's demand. To
forecast a cycle, the model is asked for all 14 future days, each estimate is
clipped at zero, and the 14 values are added together.

## Nonnegative predictions and rounding

Each daily prediction is clipped with `max(0.0, value)` **before** aggregation,
because demand cannot be negative on any single day. The cycle total is
therefore nonnegative by construction.

In the default run the clip never binds: the smallest raw daily prediction is
about `0.55` units. A test records this fact rather than assuming it.

Predictions are **not rounded** before evaluation, matching Phase 7A. Rounding
is applied only for display.

## Metrics and fair comparison

Phase 7B compares three methods on the same 27 product-cycle observations with
the same actual values, reusing the Phase 7A metric functions without change:

- Previous completed cycle baseline.
- Expanding weekday-mean candidate.
- Trained linear model.

Mean absolute error in demand units is the primary metric. Weighted absolute
percentage error is the secondary aggregate metric, calculated exactly as
`100.0 * sum(abs(actual - prediction)) / sum(actual)`. WAPE may exceed 100.0 and
is `None` only when total actual demand is zero.

Results are classified as a tie only when
`math.isclose(candidate, baseline, rel_tol=0.0, abs_tol=1e-9)` is true. Per
product, the model is compared against the baseline and against the candidate
separately. The project defines no passing accuracy threshold and no combined
accuracy score. Phase 7B remains valid if the trained model loses.

## Expected result

**The trained model is expected to match the expanding weekday-mean candidate
and to lose to the previous-cycle baseline. This is a valid and informative
result, not a defect.**

The reason is arithmetic, not luck. The first synthetic date is a Tuesday, each
training window is 14, 28, or 42 days, and each target window is 14 days.
Every window therefore contains each weekday an equal number of times. Ordinary
least squares makes residuals orthogonal to every feature column, including the
product indicators, so the mean fitted value over a product's training rows
equals that product's observed mean. Because the weekday counts are balanced,
summing the model's 14 target-day estimates returns exactly 14 times that
product's pre-origin mean demand. The Phase 7A candidate reduces to the same
quantity, since averaging each weekday and summing over a balanced window is the
same calculation reorganized.

The default results are:

| Method | MAE in demand units | WAPE percent |
| --- | ---: | ---: |
| Previous completed cycle baseline | 3.4074074074074074 | 6.375606375606376 |
| Expanding weekday-mean candidate | 3.462962962962963 | 6.4795564795564795 |
| Trained linear model | 3.462962962962963 | 6.4795564795564795 |

Per product the model ties the candidate nine times out of nine, and records
five wins and four losses against the baseline — the same split the candidate
records. The model and candidate cycle totals agree to within about `7e-14`
units, which is floating-point noise well inside the approved `1e-9` tie
tolerance.

The useful conclusion is that a trained model does not beat a well-chosen naive
baseline on a short, stationary, weekday-balanced synthetic series. The value of
Phase 7B is the walk-forward protocol, the executable leakage boundary, the
reproducible pipeline, the test suite, and this honest negative result.

## Record contract

Phase 7B adds a separate `ML_FORECAST_RECORD_COLUMNS` contract. The frozen
Phase 7A `FORECAST_RECORD_COLUMNS` schema is not modified or extended.

| Column | Type | Meaning |
| --- | --- | --- |
| `forecast_origin_date` | ISO date string | Delivery-date prediction checkpoint. |
| `training_start_date` | ISO date string | Earliest available historical date. |
| `training_end_date` | ISO date string | Day immediately before the origin. |
| `target_start_date` | ISO date string | First target date; equal to the origin. |
| `target_end_date` | ISO date string | Final date in the 14-day target cycle. |
| `product_id` | string | One approved public product alias. |
| `training_row_count` | nonnegative integer | Rows used to fit this origin's model. |
| `actual_demand_units` | nonnegative integer | Actual target-cycle demand total. |
| `baseline_prediction_units` | nonnegative integer | Previous-cycle total. |
| `candidate_prediction_units` | nonnegative float | Expanding weekday-mean total. |
| `model_prediction_units` | nonnegative float | Trained-model cycle total. |
| `baseline_absolute_error_units` | nonnegative integer | Baseline absolute error. |
| `candidate_absolute_error_units` | nonnegative float | Candidate absolute error. |
| `model_absolute_error_units` | nonnegative float | Model absolute error. |

`product_id` and the weekday derived from the target dates are the only model
inputs. `actual_demand_units` and the three error columns are evaluation-only
values. `training_row_count` is a leakage audit field: it must equal
nine times the number of dates strictly before the origin. The remaining date
columns are presentation and timing fields.

Records remain in memory. Phase 7B adds no generated CSV and no CLI.

## Reproducibility

`LinearRegression` is a closed-form least-squares solve. It uses no randomness,
so `random_state` is not applicable and is deliberately not introduced. Seed 42
in `config/generation.yaml` seeds the **synthetic data generator**, never the
model fit; the two must not be confused.

Determinism comes from four fixed choices: stable input row order inherited from
the validated Phase 3 record contract, one-hot category lists taken from
configuration instead of from the data, the two-step pipeline, and a bounded
dependency on `scikit-learn>=1.6,<2.0`.

Results are compared with `pytest.approx` rather than exact equality, because
least-squares output can differ in the last few bits across platforms and
linear-algebra builds. For the same reason Phase 7B does **not** add a SHA-256
hash of model predictions. The existing Phase 3, Phase 4A, and Phase 4B byte
hashes remain appropriate because that code is integer arithmetic with no
floating point, and Phase 7B leaves all three unchanged.

No trained model is serialized. There is no repository requirement for model
persistence, and a stored binary would add a version-coupled artifact with no
testing value.

## Dependency

Phase 7B adds one optional dependency group so the core package stays
installable with PyYAML alone:

```toml
ml = [
    "scikit-learn>=1.6,<2.0",
]
```

`src/smartstock/ml_forecasting.py` is the only module that imports
scikit-learn. No existing module imports it, so `smartstock.config`,
`smartstock.generator`, `smartstock.inventory`, `smartstock.ordering`, and
`smartstock.forecasting` remain importable without the `ml` group. NumPy is not
declared directly because no project module imports it.

## Limitations and boundaries

- The dataset contains only 56 deterministic synthetic days and three
  evaluation cycles.
- The 126, 252, and 378 training rows rest on only 14, 28, and 42 distinct
  dates. Weekday effects at the first origin are estimated from two dates per
  weekday, so the row count overstates the available evidence.
- The generator draws demand independently per product, so there are no shared
  daily shocks. Real retail demand would not behave this way.
- The generator's weekday pattern is a configured `+1` adjustment, so the model
  is learning project-authored rules rather than customer behavior.
- Real-world generalization cannot be established from synthetic data.
- Forecasts are not fed into ordering, inventory simulation, or optimization.
  Phase 7B adds no dashboard, API, or deployment, and does not begin Phase 8.
